# ClientDesk — Веб-система учёта и обработки клиентских заявок

Промышленное full-stack решение для автоматизации службы клиентской поддержки и сервисного обслуживания (CRM / Service Desk). Позволяет менеджерам регистрировать клиентов, создавать заявки, назначать ответственных сотрудников, контролировать дедлайны и закрывать проверенные задачи. Исполнители работают в едином личном кабинете с задачами, фиксируют результат и отправляют работу на проверку.

## 🚀 Быстрый запуск

### Вариант 1: Запуск всего стека одной командой через Docker Compose
```bash
# Клонируйте репозиторий и перейдите в корень:
cd clientdesk

# Скопируйте файл переменных окружения:
cp .env.example .env

# Запустите все сервисы (PostgreSQL + Spring Boot Backend + Frontend SPA):
docker compose up --build -d
```
После старта контейнеров система доступна по адресам:
- **Веб-интерфейс**: [http://localhost:3000](http://localhost:3000)
- **Spring Boot REST API**: [http://localhost:8080](http://localhost:8080)
- **Swagger / OpenAPI 3 UI**: [http://localhost:8080/swagger-ui.html](http://localhost:8080/swagger-ui.html)
- **OpenAPI Спецификация**: [http://localhost:8080/v3/api-docs](http://localhost:8080/v3/api-docs)

### Вариант 2: Локальная разработка (Node.js Full-Stack)
```bash
npm install
npm run dev
```
Сервер запустится на [http://localhost:3000](http://localhost:3000).

## 🔄 Жизненный цикл заявки (State Machine)

Переходы состояний строго контролируются на бэкенде:
```
           ┌──────────────────────┐
           │         NEW          │
           └──────────┬───────────┘
                      │ (Принять в работу)
                      ▼
        ┌────────────────────────────┐
   ┌───►│        IN_PROGRESS         │◄─────────┐
   │    └──────────┬───────▲─────────┘          │
   │               │       │                    │ (Возврат на доработку:
   │ (Уточнение    │       │ (Возобновить       │  комментарий обязателен,
   │  получено)    ▼       │  работу)           │  только MANAGER)
   │    ┌──────────────────┴─────────┐          │
   └────┤    WAITING_CLARIFICATION   │          │
        │  (Причина обязательна)     │          │
        └────────────────────────────┘          │
                      │                         │
                      │ (Передать на проверку,  │
                      │  результат работы)      │
                      ▼                         │
           ┌─────────────────────────┐          │
           │        ON_REVIEW        ├──────────┘
           └──────────┬──────────────┘
                      │ (Проверить и закрыть,
                      │  только MANAGER)
                      ▼
           ┌─────────────────────────┐
           │         CLOSED          │ (Конечный статус)
           └─────────────────────────┘
```

- Любая попытка недопустимого перехода возвращает **HTTP 409 Conflict** с понятным описанием ошибки.
- Попытка исполнителя выполнить действия менеджера (закрыть заявку, изменить клиента или параметры) возвращает **HTTP 403 Forbidden**.
- **Просрочка (Overdue)** вычисляется динамически: `dueDate < Сегодня` и `статус != CLOSED`. Это вычисляемый признак, а не статический статус.

## 📖 Краткая инструкция пользователя

### Для Менеджера (MANAGER)
1. **Регистрация клиента**: В разделе «Клиенты» нажмите «Добавить клиента», заполните наименование, телефон, email и контактное лицо.
2. **Создание заявки**: Нажмите «Зарегистрировать заявку» (на дашборде или в реестре заявок). Выберите клиента, введите тему, описание, вид услуги, приоритет, назначьте исполнителя и дедлайн.
3. **Контроль сроков**: На главной панели отслеживайте блок «Просроченные» (выделен красным) и воронку жизненного цикла.
4. **Проверка и закрытие**: Когда заявка переходит в статус `ON_REVIEW`, откройте её карточку:
   - Если результат удовлетворяет требованиям: нажмите **«Проверить и закрыть»** (статус изменится на `CLOSED`, зафиксируется дата закрытия).
   - Если требуются правки: нажмите **«Вернуть на доработку»** с обязательным комментарием, что необходимо исправить.
5. **Отчёты**: Перейдите в раздел «Отчёты», выберите период дат, ознакомьтесь с распределением нагрузки по инженерам и выгрузите реестр кнопкой **«Экспорт в CSV»**.
6. **Управление сотрудниками**: В разделе «Пользователи» можно создавать новые учётные записи и отключать доступ сотрудникам.

### Для Исполнителя (EXECUTOR)
1. **Раздел «Мои задачи»**: Отображает только назначенные вам открытые заявки, отсортированные по ближайшим срокам исполнения.
2. **Взятие в работу**: Откройте заявку со статусом `NEW` и нажмите **«Взять в работу»** (`IN_PROGRESS`).
3. **Если не хватает данных**: Нажмите **«Запросить уточнение»**, обязательно указав причину (что запрошено у клиента). Статус станет `WAITING_CLARIFICATION`.
4. **Фиксация комментариев**: В процессе работы пишите комментарии в блоке «Комментарии к заявке» для сохранения промежуточных шагов.
5. **Сдача работы**: Завершив задачу, нажмите **«Передать на проверку»**, заполнив поле «Итоговый результат выполненной работы». Статус изменится на `ON_REVIEW` и перейдёт менеджеру на верификацию.

## 🧪 Запуск приёмочных тестов

### Контрольный сценарий (7 шагов + негативные тесты)
Запуск автоматического теста через Node.js CLI:
```bash
node scripts/run_acceptance_test.mjs
```
Или прямо в веб-интерфейсе: нажмите зелёную кнопку **«Автотесты»** в шапке приложения. Запустится скрипт, проверяющий:
1. Авторизацию ролей (MANAGER и EXECUTOR)
2. Добавление клиента и регистрацию заявки
3. Назначение сотрудника и срока
4. Приёмку в работу исполнителем (NEW → IN_PROGRESS)
5. Добавление комментария и сдачу на проверку с фиксацией результата (IN_PROGRESS → ON_REVIEW)
6. Проверку и закрытие менеджером (ON_REVIEW → CLOSED)
7. Поиск по теме/номеру и верификацию журнала аудита (Audit History)
8. Отражение в отчётах и дашборде
9. **Негативный тест 1**: Исполнитель получает **403 Forbidden** на попытку закрыть заявку
10. **Негативный тест 2**: Недопустимый переход статуса отклоняется с кодом **409 Conflict**

### JUnit 5 + Testcontainers на Backend
```bash
cd backend
mvn test -Dtest=AcceptanceTest
```

## 💾 Резервное копирование БД (PostgreSQL)

В проект включен скрипт `scripts/backup.sh` для создания сжатых резервных копий с помощью `pg_dump`:
```bash
# Ручной запуск бэкапа:
./scripts/backup.sh
```

### Настройка запуска по расписанию (Cron)
Для ежедневного создания бэкапа в 02:00 ночи с хранением копий за 14 дней добавьте запись в `crontab -e`:
```cron
0 2 * * * /path/to/clientdesk/scripts/backup.sh >> /var/log/clientdesk_backup.log 2>&1
```

## 🔒 Развёртывание в Production с HTTPS (Reverse Proxy)

В каталоге `infra/` подготовлены готовые конфигурации обратного прокси:
1. **Nginx** (`infra/nginx.conf`): пример настройки SSL Let's Encrypt, HTTP/2, заголовков безопасности HSTS, CSP и проксирования API на порт 8080.
2. **Caddy** (`infra/Caddyfile`): современный веб-сервер с автоматическим выпуском и обновлением SSL-сертификатов Let's Encrypt «из коробки» без дополнительных скриптов.

## 📝 Логирование событий (Audit Event Log)

Все критические бизнес-события (вход, создание заявок, смена статусов, назначение исполнителей, сброс данных) автоматически протоколируются с отметкой времени в отдельный файл:
```
logs/events.log
```
Формат записи:
```
[2026-10-09T15:08:54.492Z] [USER: admin] [ACTION: TICKET_CREATED] Создана заявка №1016: Настройка отказоустойчивого кластера PostgreSQL Patroni
[2026-10-09T15:08:54.502Z] [USER: ivan] [ACTION: TICKET_STATUS_CHANGED] Заявка №1016: NEW -> IN_PROGRESS
```
Менеджер может просматривать журнал в реальном времени через кнопку **«Журнал»** в верхнем меню.

## 📐 Допущения и архитектурные решения

1. **Просрочка (Overdue)**: Реализована как вычисляемое свойство (`dueDate < Today && status != CLOSED`), что гарантирует актуальность признака без необходимости запуска ночных крон-джоб для мутации базы.
2. **Нумерация заявок**: Стартует с 1001 через последовательность (`sequence`) для удобства клиентов и сотрудников.
3. **Хранение паролей**: Все пароли захэшированы с использованием алгоритма BCrypt (cost factor 10). Пароли в открытом виде нигде не хранятся и не передаются в ответах API.
